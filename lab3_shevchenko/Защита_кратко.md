# Кратко для защиты

«В третьей лабораторной я изучила множественное наследование, MRO и super().
Сначала реализовала сотрудников, затем слои нейросети по второму варианту.
Для общей части задания разработала аналитическое ядро с миксинами,
обучением kNN, расчётом ROI и экспортом JSON. Проверила решение 14 тестами».

- **Множественное наследование** — класс получает поведение нескольких
  родителей. Например, Manager наследует Employee и ManagerSkills.
- **MRO** — порядок поиска методов. Python строит его по C3-линеаризации.
  Посмотреть можно через `Class.__mro__`.
- **super()** — вызов следующего подходящего метода по MRO фактического
  объекта. В гибридном объекте после MLModel идёт EconomicIndicator.
- **Миксин** добавляет одну функциональность: проверку, кэш, журнал или экспорт.
- **Конфликт методов**: если родители содержат work, автоматически выбирается
  первый по MRO. В TeamLead я переопределила work и явно вызвала обе реализации.
- **Ромб**: родители имеют общего предка. В кооперативной цепочке каждый
  конструктор вызывает super() один раз; BaseComponent инициализируется один раз.
- **Слои** возвращают строки forward/backward по заданию. Это демонстрация
  наследования, а не полноценная реализация нейросети.
- **kNN**: прогноз равен среднему значению y у k ближайших x.
- **Подбор k**: исключаю одну точку, прогнозирую её по остальным,
  усредняю квадрат ошибки; выбираю k с наименьшей LOO MSE.
- **ROI**: `(выручка − затраты) / затраты × 100 %`.
  При прогнозе 450 и затратах 300 получается 50 %.
- **Кэш** сохраняет прогноз; после переобучения или загрузки данных очищается.
- **Ошибки**: неправильные типы и данные, недопустимое k, прогноз до обучения,
  деление на ноль. Все эти случаи проверяются.

Не путай MRO и `init_trace`: MRO — порядок поиска, а trace в программе
показывает завершение конструкторов после возврата из super().
MAE и RMSE в примере вычислены на обучающих данных: это не независимая
проверка качества. Для подбора k отдельно используется leave-one-out.
